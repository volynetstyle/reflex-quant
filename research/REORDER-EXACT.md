# Exact witnesses before indexed enumeration

## Protocol

The reference kernel is identical to `0d37b93`. The indexed-only bundle
from `f9c1422` is the previous performance control. The old
`deep-shuffle` has fan-out nine and the target is the last subscriber.
`SCAN` covers the first eight. Verify separately whether the pair is
cheap to find, whether it was accepted in this execution, and how
expensive the remaining address enumeration is.

1. Use the existing source tail as a positive pair certificate. At
   promotion, mark the unread suffix for a head or tail hit. In the
   marked path, check both endpoints before the existing bounded forward
   scan. Keep cursor hits, stable allocations, node shape and edge shape.
   Prediction at width 4096 for fixed head, fixed tail and mixed head/tail
   is zero indexes. The old tail case should reach ≤0.85 of Quant in two
   independent timing jobs. All local timing controls have a 1.03 gate.
2. Isolate `SKIPPED` as a separate variant and combine it with the source
   tail only after checking each separately. At eight swaps the wide
   work should vanish at 1024, 4096 and 8192. This claim is structural.
3. Run fan-outs 4, 8, 9, 16, 32 and 64 with fixed endpoint, boundary
   and interior ranks. Use stationary random ranks per source and a
   separate mixed head/tail case. Once any interior read is beyond all
   endpoint and prefix certificates, an early same-set permutation
   remains eligible for an index.
4. If there is a residual, measure the same tail-aware kernel first
   with the previous vector and then with learning confined to the
   index transaction. Count total edges and unread edges inside the
   existing traversal. Count completion using the final cursor at the
   current tail, not the identity of the old tail. Capture a candidate
   vector in the third qualifying traversal. Use a global capacity policy
   for production-shaped trials. Repeated random interior has a 0.85
   target relative to the tail-aware control. Local controls retain
   the 1.03 gate.

Use checksummed fresh processes, seven randomized paired rounds, byte
identity for A/A, and separate structural counting. Baseline structural
assertions that pin the old resolver choice must be identified individually
if the new proof changes them. A scope-qualified improvement requires
at least two independent runners. Changes belong to experimental source
copies until reviewed against the contract.

## Comparison cells

`tail-window` adds exactly one predecessor of the source tail. It has a
fixed boundary workload at rank 63/64 and an interior control at 33/64.
`transaction` and `resident` both start from `tail-window`. The old vector
remains in two comparison cells, with and without `tail`. Compare the new
vectors to `tail-window` at the same rank and in the same round. Also retain
the comparison to `tail` specified above. Compare `resident` to `transaction`
to isolate the price of filling and clearing slots. Residency can retain
one live index, with a capacity of 8193 edges, and still has to mark unread
relations each time it starts a new pass.

The resident proof covers replacement on idle overlap, LIFO restoration
when the owner is active, and eviction on failure, membership change and
disposal. Its separate runtime checks reflect the changed internal slot
invariant. The other variants are checked with the original at-rest slot
invariant. A fixed random-rank seed is shared across variants and repeated
jobs. It creates a balanced mix of ranks at each tested width.

## Результат структурного эксперимента

`firstSub.prevSub` даёт точный адрес ребра к последнему подписчику. Для
старого `deep-shuffle` восемь holders ставят исследуемый consumer на
девятую позицию. При `SCAN = 8` исходный `pair()` возвращает `undefined`.
Если принять хвост как положительное свидетельство, достаточно одного
прохода с `UNREAD` по суффиксу. Повторные чтения затем находят пару по
голове, хвосту или старому ограниченному проходу. В ходе вложенного чтения
подписчик может переместиться с хвоста внутрь, поэтому переход к полному
индексу сохраняется. Отдельная проверка переносит подписчика внутрь уже
после начала пометки и проверяет следующее исполнение после записи и
повторного чтения того же source (P5).

При ширине 4096 измерены средние счётчики по 256 проходам после прогрева.
`Пометки` — число обходов суффикса с `UNREAD`. Последний столбец сравнивает
число посещений рёбер в пометке и открытии индекса вместе. Очистка слотов
считается отдельными счётчиками в `resident`.

| Сценарий | Сборка | Индексы | Пометки | Посещения, Quant → сборка |
| --- | --- | ---: | ---: | ---: |
| `deep-shuffle@4096`, `rank.9.9@4096` | `tail` | 0 | 1 | 4097 → 4096 |
| Фиксированный первый подписчик | `tail` | 0 | 1 | 4096 → 4096 |
| Фиксированный хвост, fan-out 4/8/9/16/32/64 | `tail` | 0 | 1 | 4097 → 4096 |
| `rank.64.ends@4096`, пополам голова и хвост | `tail` | 0 | 1 | 7169 → 4096 |
| `rank.64.63@4096`, предпоследний | `tail-window` | 0 | 1 | 4097 → 4096 |
| `rank.64.33@4096`, фиксированный внутренний ранг | `tail-window` | 1 | 0 | 4097 → 4097 |
| `rank.64.random@4096`, разные ранги источников | `tail-window` | 1 | 0,25 | 4097 → 5121 |

На чистом хвосте остаются 4096 пометок и около 4088 хвостовых совпадений
за проход. Из работы исчезают 4097 записей `source.slot` и их очистка.
В случайном случае начальный miss в четверти проходов встречает пару на
границе списка и выбирает пометку. Один из последующих miss всё равно
достигает внутренней пары и запускает индекс. Расширение окна с хвоста на
одного соседа полностью покрывает ранг 63/64. При ранге 33/64 и случайном
распределении сохраняется один индекс за проход. На случайных рангах при
ширине 1024 виден один индекс и ноль предварительных пометок.
Внутренние ранги при fan-out 4 и 8 тоже вызывают индекс. Там адрес
пары уже легко находится в префиксе, а индекс выбирает `begin` для
последующих чтений. Это решение политики, тогда как ранг 33/64 скрывает
сам адрес от всех проверенных границ.

`SKIPPED` проверен отдельной сборкой, затем вместе с `tail`. В
`swaps-nested@8` среднее число посещений рёбер в широких пометках меняется
с 380, 1916 и 3964 при ширинах 1024, 4096 и 8192 соответственно до нуля.
При 16 вложенных перестановках на ширине 1024 первый широкий обход снова
возникает. Этому предшествует miss без достаточного свидетельства
`SKIPPED`. [Тест с разными ширинами](./reorder-skipped.mjs)

Прежний `indexed-only` обучается в старом `deep-shuffle`. В сборке
`tail-vector` обучение там исчезает, так как пропадает его вход через
индекс. В двух прошлых CI-повторах `indexed-only` занимал 0,905 и 0,737
времени Quant на старой нагрузке. Эти числа относятся к исходному
девятому подписчику. Они дают контроль для новой серии с распределёнными
и фиксированными внутренними рангами. [Прежние замеры](./REORDER-LEARNING.md)

## Какие факты даёт существующее состояние

| Где возникает работа | Факт, который требуется установить | Достаточное свидетельство |
| --- | --- | --- |
| Cursor hit в `read` | Очередное ребро уже существует и впервые прочитано | `cursor.nextDep`, либо `firstDep` при пустом cursor. На чтении записывается текущий `source.ver` |
| Повтор у cursor | Пара уже принята в этот проход | `cursor.from === source`. Первая наблюдённая версия сохраняется |
| Поиск с конца списка consumer или ограниченный поиск после `next` | Адрес и принадлежность непрочитанному суффиксу | Совпадение `from` в известной части списка. Поиск назад в принятом префиксе аналогично доказывает повтор |
| Поиск по списку подписчиков | Адрес пары либо её отсутствие | Пустой список, полностью проверенный короткий список или совпадение `to`. `firstSub.prevSub` и его предшественник расширяют множество положительных свидетельств. Исчерпание ограниченного поиска при неисследованных подписчиках оставляет ответ неизвестным |
| `begin` / пометка суффикса | Найденная пара могла быть повтором. Следующим запросам нужен быстрый тест её положения относительно cursor | Положительный `SKIPPED` уже достаточен для конкретной пары. Иначе `UNREAD` кодирует суффикс, а его пометка выполняется один раз на этом пути |
| `index` / `slot` | Внутренний адрес пары и возможность точно доказать её отсутствие | Полное перечисление заполняет `source.slot`. Проверка `slot.to` валидна внутри области владения; принадлежность непрочитанному суффиксу по-прежнему даёт `UNREAD` |
| `unindex`, `cutDeps`, `settleDeps` | Вернуть вытесненные ячейки, удалить непрочитанные зависимости, сохранить проверку поколения после оборота счётчика | Это изменения графа и состояния. `last.nextDep` уже задаёт границу удаления. `edge.gen` указывает на tentative birth, независимо от того, приняли ли ребро в этот проход |
| Отложенная реконструкция | Порядок зависимостей в фактическом порядке первых чтений (D1) | Cursor и перестановки поддерживают этот порядок по ходу прохода. В deferred-сборке нужно записать последовательность первых чтений и затем восстановить связи. Перенос записи сохраняет семантику и остаётся широким в испытанных реализациях |

`SKIPPED` безопасен после прежнего неудачного прохода. В текущем проходе
принятие любого ребра записывает неотрицательную версию. Значит, ребро с
`SKIPPED`, найденное вне cursor hit, ещё не принято в текущем префиксе.
Точное совпадение пары вместе с этим условием разрешает одно обычное
перемещение и запись версии. Как и прежде, повтор её не обновляет.
[Лемма о непрочитанном ребре](../CONTRACT.md#implementation-lemma-for-skipped)

Для bounded resolver конечный префикс источника и хвостовое окно могут
одновременно оставить нужное ребро и внутреннюю часть списка consumer
за пределами просмотренного. Возьмём две такие конфигурации с одинаковыми
cursor, видимыми участками обоих списков и пустым `slot`. В первой искомая
пара существует внутри обоих списков. Во второй на непросмотренных
позициях взяты две другие пары, а искомой нет. Совпадающие поля снаружи
этих позиций дают одинаковые результаты проверок, хотя resolver должен
переместить старое ребро в первой конфигурации и создать его во второй.
Остаточный случай установлен для проверенного набора свидетельств.
Существует близкое отдельное доказательство отсутствия на границе
бюджета, если дальнейшие подписчики исчерпаны уже проверенным хвостом.
В этой серии ветвление для него оставлено за пределами эксперимента.

## Обучение внутри индекса и сохранение слотов

Сборка `transaction` начинает наблюдение в `index()`. Существующий обход
даёт ширину `d`, длину `u` непрочитанного суффикса и признак tentative
рёбер. Очистка в `unindex()` уже проходит весь список. Совпадение
ширины, отсутствие tentative, успешный выход и `last.nextDep === null`
вместе доказывают завершённый проход по прежнему множеству отношений.
Все `u` непрочитанных рёбер оказались приняты. Старый `lastDep` по
идентичности для этого вывода не требуется, так как перестановка могла
его изменить. Пер-чтение `recordMoved()` заменяет проверка `u ≥ 32` и
`4u ≥ 3d`. Смена `gen` между транзакциями учитывает пробел успешных
исполнений. Счётчик служит эвристике повышения уровня. Исключение без
индекса не регистрирует отдельного наблюдения.

На третьей подходящей транзакции сам `index()` собирает ссылки. Порядок
массива отражает момент заполнения слотов. Вектору нужен набор точных
адресов, а порядок графа определяется фактическим чтением через cursor.
В первых трёх исполнениях `rank.64.random@4096` получено `d = 4097` и
`u = 4096, 4094, 4096`. Счётчик сбора вектора даёт `0, 0, 4097` за эти
проходы. В четвёртом работает уже собранный массив.
Обёртка `fn` появляется только после повышения. При ошибке, добавлении
или удалении отношений либо совпадении конечных рёбер со старым порядком
она снимается. Последнее условие эвристическое и может снять специализацию
на перестановке только внутренних рёбер. Обе сборки имеют один глобальный
допуск на вектор. При 8193 рёбрах он заполнен, при 8194 сборки продолжают
временное индексирование. Счётчики наблюдений находятся в `WeakMap` для
реально индексировавшихся consumers, а глобальный допуск держит слабую
ссылку на специализированный consumer и его состояние.

`resident` хранит только пары из этого же вектора. На успешной широкой
перестановке с прежним множеством и без вытесненного внешнего слота
сохраняется один владелец. На следующем проходе отмечаются `UNREAD` все
старые рёбра, после чего resolver использует уже записанные адреса.
Чужой индекс вытесняет спящий cache при первом пересечении. Вложенный
индекс при активном владельце пользуется существующим стеком LIFO и
возвращает точную внешнюю ячейку. Отдельный teardown обрабатывает
disposal спящего владельца. Ошибка до первого чтения и добавление нового
отношения в теле тоже сбрасывают cache. На повторяющемся `rank.64.random`
после прогрева счётчики дают 4097 пометок, одну повторно использованную
резиденцию и ноль записей и очисток слотов за шаг.

Проверка на отрицательном примере оставляет `slot` без нового протокола.
Первое новое чтение старой пары принимается за повтор, зависимость
отрезается, следующая запись не будит consumer. Другая проверка
оставляет в ячейке адрес снятого ребра после `dispose`. Значит, для
резиденции нужна явная область владения и инвалидация. Обычная проверка
`checkGraph` требует пустых слотов между проходами. Для эксперимента
с резиденцией проверены альтернативное владение и отдельные тесты
публичной семантики. В полном DEV-наборе `resident` проходит 450 из
451 проверок. Проверка `history-erasure` останавливается на сохранённом
слоте в покое. В целевых наборах проходят 84 DEV и 78 PROD тестов с
шестью DEV-only пропусками в PROD.

Порог 0,85 для `tail` на исходном `deep-shuffle` отвергнут. Хвост
даёт O(1) доказательство адреса и убирает индекс структурно. В режиме
пометки каждое далёкое чтение снова ищет адрес через список подписчиков,
тогда как плотный индекс даёт `source.slot` напрямую. На этой паре
заданий Quant и `tail` не регистрировали GC в измерительной фазе.
Счётчики не измеряют задержку зависимых загрузок и не позволяют
приписать всё различие одному участку машинного кода.

В случайных рангах прежний вектор выиграл на обоих раннерах и выполнил
порог 0,85 относительно `tail`. В двух дополнительных заданиях у этого
сравнения получено 0,837 и 0,782. На фиксированном ранге 33/64 прежний
вектор даёт разные направления в исходной паре заданий. Сохранение одного
обращения к индексу в структурных счётчиках совместимо с обоими результатами.

`resident` он пройден на обоих раннерах при ширине 4096. В прогретом
случае резиденция сокращает время на 24,5% и 21,9% относительно того же

и порог 0,85 относительно `tail-window` выполнен один раз. В измерении
`resident` работает один устойчивый владелец. Вытеснение при смене
владельца проверено структурно и вызывает Θ(d) очистку по ширине
вытеснённого потребителя. Временной цены этой смены данная сетка не даёт.

Фиксированный ранг 63/64 подчёркивает цену адресации. Для получения
адреса ребра через окно нужны последовательно `firstSub`, хвост и его
предшественник. При индексировании адрес лежит непосредственно в
`source.slot`. Замеры показывают 85,9% и 47,6% дополнительного времени
при устранении заполнения и очистки 4097 слотов. В этой паре заданий
A/A составляет 1,018 и 0,970.

### Разложение замедления по правкам (2026-11-19)

Сборка `transaction` состоит из пяти групп правок поверх `tail-window`:
guard в `miss`, наблюдение в `index`, новая сигнатура `unindex`, отметка
в `link`, освобождение в `dispose`. Сборки `tx-no-<группа>` убирают одну
группу, `tx-only-<группа>` оставляют одну. Медиана парных отношений
к Quant, 7 раундов, по два задания на версию Node
([workflow](../.github/workflows/reorder-shape.yml), run 44604480788):

| Сборка | Node 22.23.4 | Node 25.2.0 |
| --- | ---: | ---: |
| A/A | 0,983 / 1,011 | 0,997 / 1,012 |
| `tail-window` | 1,048 / 1,191 | 1,003 / 0,992 |
| `transaction` | **1,336 / 1,268** | 0,996 / 1,016 |
| `tx-no-miss` | **1,036 / 0,966** | 1,007 / 1,012 |
| `tx-only-miss` | **1,147 / 1,327** | 0,998 / 1,006 |
| `tx-no-index` | 1,351 / 1,319 | 0,989 / 1,007 |
| `tx-no-unindex` | 1,348 / 1,272 | 1,001 / 0,993 |
| `tx-no-link` | 1,305 / 1,321 | 0,995 / 1,001 |
| `tx-no-dispose` | 1,308 / 1,294 | 1,001 / 1,013 |
| `tx-only-index` | 1,014 / 1,003 | 0,996 / 1,016 |
| `tx-only-unindex` | 1,022 / 0,993 | 0,998 / 1,007 |

Всё замедление `lb.shuffle@4096` даёт одна правка: guard
`if (last === null && captured?.consumer === c)` в начале `miss`. Без неё
замедления нет, с ней одной оно появляется. Эффект зависит от движка: на
V8 12.4 (Node 22) он есть, на V8 14.1 (Node 25) нет ни у одной сборки.
На `lb.reverse@4096`, который тоже проходит через `miss`, эффекта нет нигде.

Значит, исполняемая работа guard-а (одно сравнение `last === null`, ложное
для всех чтений, кроме первого) замедление не объясняет. Дело в том, как
V8 12.4 оптимизирует `miss` на пути перемешивания: инлайнинг `miss` и
`settle`/`pair` или деоптимизация. Формулировка «оптимизация, которая не
исполняется» неточна: guard исполняется на каждом промахе, а выключенным
остаётся только то, что за ним. Для любой будущей интеграции вектора
проверка должна стоять вне `miss`, например в холодной ветке `index`.
Следующий шаг: `--trace-turbo-inlining --trace-deopt` на Node 22 для
`tx-only-miss` против `tail-window`.

## Вывод для Quant

Хвост и `SKIPPED` устраняют две разные причины широкой работы. Хвост
доказывает адрес пары и убирает сам индекс даже на широкой перестановке.
`SKIPPED` устанавливает непрочитанность уже найденной пары и убирает
широкую пометку для восьми вложенных обменов. Его отдельная сборка
сокращает время там на 16,1% и 10,4% и проходит все локальные контроли
с порогом 3%. Переход с `slot` на повторное чтение через хвостовые
границы увеличил время на исходном `deep-shuffle` и на ранге 63/64.

За пределами проверенных границ остаются повторяющиеся плотные
перестановки, для которых временный индекс даёт адреса. Здесь вектор
по-прежнему полезен. Сбор по ходу `index` избавляет от повторного обхода
при повышении, а явная резиденция снижает steady-state стоимость, сохраняя
пометку непрочитанных рёбер. Для обеих новых сборок решение о включении в
ядро отклонено локальным порогом. Результат задаёт нижнюю границу для
проверенных способов получения адреса и измеряет стоимость конкретных
представлений.

В 12 измерительных заданиях собрано 3430 свежих процессов с проверкой
контрольных сумм, номеров раундов и SHA сборки. Все 19 заданий CI
завершились успешно. Полные наборы для Quant, `tail`, `skipped`,
`tail-skipped`, `tail-window` и `transaction` прошли на 451 DEV и 444 PROD
тестах с семью DEV-only пропусками в PROD. Отдельное покрытие
`resident` описано выше. [Числа всех раундов](./REORDER-EXACT-RESULTS.json)
